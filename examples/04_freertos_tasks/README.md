# 04. Задачи, очередь и мьютекс

Три задачи FreeRTOS работают одновременно (на единственном ядре ESP32-C3 — по очереди, но с частым переключением):

| Задача | Что делает |
| --- | --- |
| `producer` | Раз в секунду кладёт в очередь структуру `sample_t` |
| `consumer` | Спит, пока в очереди не появится структура, потом печатает её |
| `counter` | Каждые 200 мс увеличивает общий счётчик под мьютексом |

Задача `main` раз в пять секунд пишет, что она жива и сколько элементов сейчас лежит в очереди.

Железо для этого примера не нужно: всё происходит в мониторе порта.

## Две разные задачи синхронизации

**Очередь** переносит копию данных и одновременно будит получателя. Producer не обязан знать, кто заберёт измерение. Если получатель не успевает, отправитель заснёт на `xQueueSend`, а не затрёт старые данные.

**Мьютекс** ничего не переносит. Он лишь не пускает вторую задачу в участок кода, пока первая его не отпустила. Здесь этот участок — изменение и чтение `s_shared_counter`. Без мьютекса одна задача могла бы прочитать счётчик в тот момент, когда другая записала его только наполовину.

Мьютекс нельзя брать в прерывании. Для прерывания есть очередь и функции `...FromISR`, это показано в примере с кнопкой.

## Приоритет и стек

`xTaskCreate(..., priority, ...)`: большее число — более важная задача. Если задача с высоким приоритетом никогда не спит (`vTaskDelay`, очередь, семафор), задачи с меньшим приоритетом на этом ядре не получат времени вообще.

Размер стека в ESP-IDF задаётся в **байтах**. 3072 — обычный запас для задачи, которая вызывает `ESP_LOGI`. Задаче, которая только крутит счётчик, хватает 2048. Если стека мало, в мониторе будет паника `stack overflow` и перезагрузка.

## Сборка

```bash
. $HOME/esp/esp-idf/export.sh
cd examples/04_freertos_tasks
idf.py set-target esp32c3
idf.py build
idf.py -p /dev/ttyACM0 flash monitor
```

## Что вы должны увидеть

Примерно раз в секунду:

```text
I (xxx) tasks: измерение 0 в момент 1000 мс, общий счётчик 5
I (xxx) tasks: измерение 1 в момент 2000 мс, общий счётчик 10
```

Счётчик растёт быстрее номера измерения: его увеличивают каждые 200 мс, а измерения выходят раз в секунду.

Раз в пять секунд добавляется строка от задачи `main`. Число элементов в очереди почти всегда 0: consumer забирает измерение сразу.

## Эксперимент

В `producer_task` уберите `vTaskDelay`. Очередь на 4 элемента быстро заполнится, и `xQueueSend` начнёт блокировать producer, пока consumer не освободит место. Программа не сломается: очередь как раз для того, чтобы быстрый источник подождал медленного получателя. Верните паузу после эксперимента, иначе лог будет очень плотным.
