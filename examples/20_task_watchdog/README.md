# 20. Сторожевой таймер задач

Пример пять секунд работает как обычно: раз в секунду кормит сторож и пишет номер цикла. Затем перестаёт его кормить. Через три секунды ESP-IDF фиксирует зависание задачи `main` и перезагружает чип. Следующая загрузка прямо говорит, что причина — сторож задач.

Так проверяют, что защита живая. В обычной программе, наоборот, `esp_task_wdt_reset()` стоит в конце каждого успешного прохода цикла и не пропускается специально.

## Зачем он, если есть RESET

Кнопку RESET на корпусе некому нажать, если устройство висит на стене и цикл навсегда застрял в ожидании, которое никогда не кончится. Сторож делает это сам.

Кормить его нужно из той задачи, которая и есть «признак жизни». Плохой приём — завести отдельный таймер, который вызывает `esp_task_wdt_reset` всегда: он будет кормить сторож и после того, как основная задача уже зависла. Тогда сторож ничего не стережёт.

## Несколько разных сторожей

| Сторож | Когда срабатывает |
| --- | --- |
| Задач, task WDT | Подписанная задача слишком долго не вызывала `esp_task_wdt_reset` |
| Прерываний, interrupt WDT | Прерывание не вернулось или планировщик долго не получал управление |
| RTC | Загрузка или глубокий сон длятся неправдоподобно долго |

В мониторе причины выглядят по-разному. `esp_reset_reason()` возвращает `ESP_RST_TASK_WDT`, `ESP_RST_INT_WDT`, `ESP_RST_PANIC`, `ESP_RST_POWERON` и другие. Пример печатает и имя, и число, но сравнивать в коде нужно с именем: номера перечисления — не контракт.

`ESP_RST_PANIC` — это не сторож. Так кончаются `ESP_ERROR_CHECK` на ошибке, непойманное исключение и проверка стека. Чип тоже перезагружается, но лечить это надо по тексту паники выше, а не увеличением таймаута сторожа.

## Сборка

```bash
. $HOME/esp/esp-idf/export.sh
cd examples/20_task_watchdog
idf.py set-target esp32c3
idf.py build
idf.py -p /dev/ttyACM0 flash monitor
```

Таймаут 3 секунды и паника заданы в `sdkconfig.defaults`. Паника перед перезагрузкой печатает имя задачи. Без паники был бы тихий сброс и только новая строка «причина этой загрузки».

## Что вы должны увидеть

```text
I (xxx) wdt: причина этой загрузки: включение питания (1)
I (xxx) wdt: цикл 1, сторож покормлен
...
I (xxx) wdt: цикл 5, сторож покормлен
W (xxx) wdt: больше не кормлю сторож. Через ~3 с будет перезагрузка
```

Дальше паника task watchdog и новая загрузка:

```text
I (xxx) wdt: причина этой загрузки: сторож задач (6)
```

Цикл повторяется сам. Чтобы остановить, сотрите прошивку другим примером или держите кнопку BOOT при сбросе и залейте другую программу.

## Как устроен код

ESP-IDF к моменту `app_main` уже запустил сторож (`CONFIG_ESP_TASK_WDT_INIT`). Задача на него не подписана, пока кто-то не вызовет `esp_task_wdt_add`. Аргумент `NULL` подписывает текущую задачу.

Пока подписка есть, пауза длиннее таймаута без `esp_task_wdt_reset` считается зависанием. `vTaskDelay` сторож не кормит: с точки зрения сторожа спящая задача тоже молчит. Поэтому таймаут ставят больше самой длинной законной паузы в этой задаче.

Системные задачи простоя на C3 тоже могут быть подписаны настройкой `CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0`. Их трогать не нужно: они кормят сторож сами, пока планировщик жив.
